# 단순화 계획

**규정(법령) 개정을 읽어 바뀐 점을 찾고, 업데이트해야 할 상품 정보를 제안하고, 확인 뒤 반영한다.**
2026-10-20 팀 합의와 리뷰 피드백을 반영했다. 기준: main(#11 MCP 머지), `feature/agent`(ed4034b).

## 결정 사항

| 항목 | 결정 |
|---|---|
| 대상 | 코드 수정 대신 **상품 규칙(`product_rules`) 업데이트 제안** |
| 역할 · 권한 | **없음.** 담당자 · 개발자 구분, 역할별 권한, 계정 전환을 모두 뺀다. 로그인은 남긴다 (인증 항목) |
| 사람 확인 | **1번.** 로그인한 사용자가 제안마다 반영 / 제외를 고르고 반영한다 |
| 실제 반영 | **한다.** 상품 규칙 새 버전을 등록한다 (MCP 변경 도구 · 대기열 항목) |
| 제안 검증 | **한다.** 입력만으로 결정되는 것만 검사한다. 정답지는 쓰지 않는다 |
| 빠지는 것 | 코드 검색 · 코드 수정안 · 테스트 생성 · 샌드박스 검증 · Draft PR · 작업 티켓, code-mcp |

## 2. 흐름

```
업로드 ─▶ 바뀐 조항 추출 ─(실질 변경 0건)─▶ 종료(NO_CHANGE)
            │ rag-mcp(regulation-mcp): 조항 비교 · 의미 검색
            ▼
        영향 상품 규칙 찾기         business-mcp: 상품 · 규칙 · 계약 영향 조회
            ▼
        제안 작성 (규칙별 지금 값 → 제안 값, 시행일, 근거 조항)
            ▼
        제안 검증 (코드) ─(실패, 재시도 남음)─▶ 제안 작성     ← 반복
            ▼
        사용자 확인 [interrupt] ─(전부 제외 · 거절)─▶ 종료(REJECTED)   ← 상태 저장 · 재개
            │ 제안마다 반영 / 제외
            ▼
        상품 규칙 새 버전 등록      business-mcp 변경 도구 → 확인 기록 검증 → 대기열(재시도 · DLQ)
            ▼
        리포트 ─▶ 완료(DONE)
```

| 단계 | 백엔드 상태 (재사용) | 화면 표시 |
|---|---|---|
| 바뀐 조항 추출 | `EXTRACTING` | 바뀐 조항을 찾는 중 |
| 영향 찾기 | `LOCATING` | 영향 받는 상품 규칙을 찾는 중 |
| 제안 작성 | `DESIGNING` | 업데이트 제안을 만드는 중 |
| 제안 검증 | `VERIFYING` | 제안을 검사하는 중 (n차) |
| 사용자 확인 | `WAITING_REVIEW` | 제안 확인 필요 |
| 반영 | `PUBLISHING` | 상품 규칙에 반영하는 중 |
| 종료 | `DONE` · `NO_CHANGE` · `REJECTED` · `FAILED` | |

`WAITING_REQUIREMENT_APPROVAL` · `HELD`는 쓰지 않는다. 백엔드 상태 전이는 `EXTRACTING → LOCATING`만 새로 허용한다.

## 3. 제안 검증 (정답지 사용 금지)

검증 노드는 **입력(규정 diff, 상품 규칙 조회 결과)만으로 결정되는 것**을 본다. 정답지를 읽으면 Agent 입력에서 정답 힌트를 뺀 원칙(#4)과 충돌하고, 반복 루프가 자기채점이 된다.

| 순서 | 검사 | 예 |
|---|---|---|
| 1 | **단위 변환이 맞는가** (시연에서 반복이 돌게 하는 1순위) | 신 조항 "35%" → `unit: ratio`면 0.35. 1차에 35로 쓰면 실패 → 2차 0.35 통과 |
| 2 | 인용한 조항이 `diff_versions`에서 실제로 바뀐 조항인가 | 제8조 · 제15조 · 제15조의2 |
| 3 | 날짜가 맞는가 | 새 행 `effective_from` = 시행일(2026-12-01), 기존 행 `effective_to` = 전날(2026-11-30) |
| 4 | 이미 신 기준을 충족한 규칙에 제안하지 않았는가 | P003 `DSR_LIMIT 0.35` |

**함정 판단은 검증이 아니라 LLM의 몫이다.** 같은 0.40이지만 LTV, 같은 65지만 정년 같은 판단은 LLM이 근거와 함께 내고, 맞았는지는 **평가 스크립트가 정답지와 비교해 점수로** 보여준다.

## 4. 난이도: Agent의 가치가 보이게

변경 대상이 `DSR_LIMIT` 이름 검색만으로 끝나 보이지 않도록, 이미 있는 데이터로 판단이 필요한 부분을 넣는다.

| 항목 | 내용 |
|---|---|
| **시연 주인공: R010 `ELIGIBLE_MIN_AGE`** | 키 이름에 SENIOR가 없어 키워드 검색으로는 못 찾는다. 시니어 상품의 가입 기준이라는 판단으로 찾는다 |
| 경과조치 영향 | `/internal/contracts/impact`로 시행일 전 신청이라 종전 기준이 유지되는 계약(C0002, C0004)을 제안서에 함께 보인다. C0006(기간 연장 시 종전 DSR 한도)은 지금 API가 나이로만 조회하므로 조회 방법을 정해야 한다 |
| 제15조의2 새 규칙 | 기존 행이 없는 규칙을 **"새 규칙 필요"**로 제안한다 (원래 설계의 ④ 신규 유형). 규칙 키 · 단위는 데이터 담당과 정한다 |

제안 결과 (정답지 `eval/answer_key.md` 2절 기준):

| 상품 | 규칙 | 지금 | 제안 | 근거 |
|---|---|---|---|---|
| P001 직장인 신용대출 | `DSR_LIMIT` (R001) | 0.40 | 0.35 | 제8조 |
| P002 시니어 든든대출 | `DSR_LIMIT` (R011) | 0.40 | 0.35 | 제8조 |
| P002 시니어 든든대출 | `ELIGIBLE_MIN_AGE` (R010) | 65 | 60 | 제15조 |
| (새 규칙) | 고령자 설명 확인 | 없음 | 필수 | 제15조의2, 체결일 기준(부칙 제3조) |
| 대상 아님 | `MORTGAGE_LTV_LIMIT`, `INCOME_EST_RETIREMENT_AGE`, P003 `DSR_LIMIT 0.35`, `SENIOR_RATE_DISCOUNT` | | 그대로 | 같은 숫자 · 다른 의미, 이미 기준 충족, 우대 폭 변경 없음 |

## 5. 시연을 다시 할 수 있게

반영하면 업무 테이블에 v4 행이 생겨 두 번째 시연에서 "변경 대상 없음"이 나온다.

| 항목 | 정할 것 |
|---|---|
| 초기화 | 업무 테이블을 JSON 시드로 되돌리는 시연 리셋 API. 화면의 "데모 초기화"가 이것과 작업 기록을 함께 지운다 |
| 새 행 번호 | 기존 최대 번호 다음 (`R020`부터) |
| 동시 제안 | 반영할 때 지금 값이 제안 당시 값과 다르면 409 ("이미 바뀐 규칙") |
