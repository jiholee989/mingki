# Frontend 작업 계획

Rule Ripple 프론트엔드(Vue 3 + Spring 백엔드)의 작업 순서와 완료 기준.
제품 방향은 [SIMPLIFICATION.md](./SIMPLIFICATION.md), 처음 설계는 [PROJECT.md](./PROJECT.md), 백엔드 API는 [BACKEND_API.md](./BACKEND_API.md).

## 원칙

- **사용자는 한 명, 역할 없음.** 기능(바뀐 조항 → 상품 업데이트 제안 → 반영)을 보여주는 데 집중한다.
- 백엔드가 바뀌어도 안 바뀌는 것(화면, 상태 흐름, 도메인 개념)과 바뀔 것(API 주소, 응답 필드, 인증, 진행 상황 전달 방식)을 분리한다. 바뀔 것은 `src/api/`와 `src/mocks/`에만 둔다.
- 백엔드가 완성되기 전에는 MSW 가짜 서버로 모든 화면을 먼저 만든다.

| **개정 브리핑** | `/tasks/:id/briefing` (가칭) | **새로.** 아래 구성 | Card, Table · Item, Badge, Collapsible, Sheet, ToggleGroup, AlertDialog |
| 결과 · 비교 | `/tasks/:id/result` (가칭) | 리포트 · 데모 비교를 합침 | Card, Progress, Table, Badge |
| 요건 확정, 영향 위치, 검토 · 승인(diff) | | 삭제. 브리핑에 흡수 | |

개정 브리핑 구성 (위에서 아래로):
1. 요약: 규정 이름, 시행일(D-day), 실질 변경 n건, 제안 n건
2. **신구조문 대비표**: 바뀐 조항, 바뀐 글자 강조. 표현만 바뀐 조항은 접어서 "실질 변경 없음"
3. **상품 업데이트 제안**: 상품 · 규칙 · 지금 값 → 제안 값 · 시행일 · 근거 조항 · 판단 이유, 제안마다 반영 / 제외. "새 규칙 필요"는 따로 표시
4. **대상 아님**: 같은 숫자 · 다른 의미, 이미 기준 충족 + 이유
5. **기존 계약 영향**: 시행일 전 신청이라 종전 기준이 유지되는 계약
6. **자동 검사 결과**: 1차 · 2차 검증, 통과 항목
7. 아래 고정 바: "제안 4건 중 n건 반영" + [반영] (확인 대화상자)

공통: 상단바(`AppHeader`: 사용자 이름 · 데모 초기화 · 로그아웃), 작업 메뉴(`TaskNav`: 링크), 토스트(Sonner).

shadcn-vue 컴포넌트의 `data-open:` · `data-checked:` · `data-active:` · `data-horizontal:` 같은 축약 조건은 `style.css`의 `@custom-variant`로 reka-ui의 `data-state` · `data-orientation`에 연결한다. 없으면 탭 배치 · 선택 표시 · 열고 닫기 효과가 깨진다.

## 갤러리 (`/gallery`)

- 서버 · 로그인 · 기다림 없이 단계별 화면을 한 페이지에서 본다. 개발 빌드에서만 연다.
- 데이터는 `scenario(events, now)`로 원하는 단계를 바로 만든다. 단계 선택: 진행 중 · 1차 검증 실패 · 제안 확인 대기 · 반영 중 · 완료.
- 화면은 **불러오기(페이지)와 보여주기(컴포넌트)를 나눈다.** 보여주기 컴포넌트는 데이터를 props로만 받아서 갤러리와 실제 앱이 같은 컴포넌트를 쓴다.

## 데이터 · 가짜 서버 (`src/mocks/`)

| 부분 | 파일 | 하는 일 | 단순화 후 |
|---|---|---|---|
| 계산 | `scenario.ts` | 사람이 한 일과 지금 시각으로 단계와 보이는 데이터를 계산. 타이머 없음 | 단계 순서 교체, 사람이 한 일은 업로드 · 확인(반영/제외) 두 가지 |
| 저장 | `store.ts` | 작업마다 사람이 한 일. localStorage(`rr.mock.tasks.v1`), 요청마다 다시 읽음 | 저장 모양이 바뀌므로 키를 v2로 |
| 응답 | `handlers.ts` | 백엔드와 같은 검사 규칙 · 문구 | 역할 검사 제거, 제안 조회 · 확인 · 초기화 응답 추가 |
| 가짜 데이터 | `fixtures/creditLoan/` | 규정 v3 → v4 1건 | 제안 4건(R001 · R011 · R010 · 제15조의2), 대상 아님, 계약 영향(C0002 · C0004 · C0006), 1차 · 2차 검증 결과 |

- 근거: 규정 원문 `data/regulations/credit-loan-ops/`, 상품 규칙 정답 `eval/answer_key.md` 2절, 계약 3절.
- `creditLoan.spec.ts`가 원문 · 정답지와 맞는지 계속 검사한다.
- 가짜 서버의 경로는 `API_BASE`(`/api`)에 고정한다. `*/api/*`처럼 넓게 잡으면 `/src/api/*.ts` 소스 요청까지 가로챈다.

## 도메인 타입 (`src/domain/`)

백엔드 응답의 칸 이름과 값을 그대로 따른다. 자유 형식 칸(`detail`, `payload`)만 뺀다.

| 타입 | 단순화 후 |
|---|---|
| `AnalysisTask`, `TaskStatus`, `RegulationDocument`, `Requirement`, `ChangeSpec`, `Approval`, `User` | 남김 (`Role`은 화면에서 안 씀) |
| **`RuleProposal`** (가칭) | 새로. 백엔드 `rule_proposals`가 확정되면 맞춘다. 상품 · 규칙(새 규칙이면 없음) · 단위 · 지금 값 · 제안 값 · 시행일 · 종전 행 종료일 · 근거 조항 · 판단 이유 · 반영/제외 · 검증 결과 |
| **`ContractImpact`** (가칭) | 새로. 계약 · 상품 · 신청일 · 신청 당시 나이 · 종전 기준 유지 여부 |
| `CodePatch`, `TestCase`, `Delivery` | 안 씀 (S4에서 정리) |

## 화면 동작 (그대로 유지)

- 로그인 가드만 둔다: 로그인 안 했으면 `/login?redirect=…`. 로그인 상태는 탭마다 따로(sessionStorage).
- 작업 상태는 레이아웃(`TaskLayout`) 한 곳에서 1초마다 받고, 각 화면은 작업이 바뀔 때(`updatedAt`) 자기 데이터를 다시 받는다. 제출 뒤에는 최신 상태를 받은 다음 이동한다.
- 단계가 맞지 않으면 화면을 막지 않고 안내한다. 1초 폴링 중 상태가 바뀌어도 화면이 튕기지 않게.
- 로딩은 첫 로딩에만 Skeleton, 데이터가 없으면 Empty, 동작 오류는 토스트, 없는 작업은 Empty + "새 작업".
- 화면 파일을 못 불러오면(새 배포 등) 한 번만 새로고침해서 복구한다.

## 실서버 연결

바꾸는 곳은 아래 네 파일만이어야 한다.

| 파일 | 바뀌는 것 |
|---|---|
| `vite.config.ts` | 개발 서버의 `/api` 요청을 백엔드(`localhost:8080`)로 프록시 |
| `src/api/client.ts` | `Authorization: Bearer` 토큰, 에러 형식 `{error, message}`, 401이면 로그인으로 |
| `src/api/types.ts` | 응답 모양이 달라진 항목. 도메인 타입이 응답과 같아서 변환 층은 두지 않는다 |
| `src/composables/useTaskPolling.ts` | `GET /tasks/{id}` + `/events?after=` 폴링 (SSE는 나중에) |

## 배포

- frontend 컨테이너(nginx)가 빌드 결과를 서빙한다. history 라우팅은 `try_files $uri /index.html`.
- `/api` 요청은 nginx가 backend로 넘긴다.
- `docker-compose.yml`의 frontend 서비스 주석을 푼다.

## 백엔드와 맞출 것

| 항목 | 상태 |
|---|---|
| 제안 조회 · 확인(반영/제외) API, `rule_proposals` 모양 | 백엔드(C) 작업 후 확정 |

| history 라우팅 | frontend nginx가 처리 (확인됨) |
