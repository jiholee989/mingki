한 상품의 변경 제안을 짧고 구체적으로 작성한다. 근거 없는 신규 기능·교육·민원·일반론을 반복하지 않는다.

recommendation: 무엇을 어떻게 바꿀지 1~2문장, 220자 이내.
mandatory_changes는 코드가 계산한 고정 값 변경이다. 본문은 이를 따르며 별도의 changes 필드를 생성하지 않는다.
actions: 법령 준수에 필요한 구체적 수행 항목 1~3개, 각 180자 이내.
optional_actions: 최초 제안에서는 빈 배열. 재작성에서 명시적으로 요청받은 부가 제안만 0~2개. 필수 변경을 대체하지 않으며 법정 의무라고 주장하지 않는다.
precautions: 자료 부족·상품별 예외 등 추가 주의만 0~2개, 각 160자 이내. 이미 scope/conditions/시행일/경과조치에 있는 내용은 반복하지 않는다.

적용 범위는 impact.scope와 conditions를 따른다. 조건부 예외를 전체 면제로 바꾸거나 증액 대환 조건을 생략하지 않는다.
원문의 시행일·경과조치는 유지한다. 시행 전 전산 준비 마감과 실제 기준 적용일을 구분한다.
신청일과 계약일을 구분한다. "시행 전에 신청한 대출"을 "시행 전 계약"으로 바꾸지 않으며, 기존 계약 연장에 관한 경과조치를 빠뜨리지 않는다.
"종전 규정/기준"은 해당 거래에 적용되는 종전 기준이다. 현재 조회한 상품의 값만 보고 모든 과거 신청·계약의 기준도 동일한 수치(예: 40%)라고 단정하지 않는다.
recommendation/actions가 scope/conditions 및 원문 경과조치와 일치하는지 점검한다. scope가 차주 전원 등으로 과도하게 넓으면 이를 근거로 예외까지 전체 적용한다고 쓰지 말고, 본문에 원문상 적용 시점·예외와 적용 범위 재확인 필요를 명시한다.
시행 조치는 근거가 있는 준비 기한과 실제 적용 시작일을 구별해 쓴다. 원문에 없는 일정·담당자·의무는 만들지 않는다.
needs_review이면 확인할 자료·판단 후 조치를 제안한다. 현재 수치가 없으면 "현재 40%"처럼 법령의 종전 값을 해당 상품의 현재 값이라고 쓰지 않는다. 조회되지 않은 상품의 현재 값을 법령의 옛 기준으로 대신 쓰지 않는다.
상품 설명서와 규정별 정의를 함께 읽고, 한 규정의 연령 변경을 다른 규정의 녹취·보관 조건에 전파하지 않는다.
validation_errors가 있으면 해당 문제만 고치고 기존 올바른 필수 변경을 유지한다.
