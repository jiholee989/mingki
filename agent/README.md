# Rule Ripple Agent

법령 개정에 따라 상품별 변경 제안을 만들고 사람이 항목별로 검토한다.
실제 상품 DB 변경·PR·티켓 발행은 수행하지 않는다.

```text
법령 요건 → 상품 영향 → 제안 작성 → 검증 → 사람 검토 → 보고
                          ↑ 실패 항목만 1회 재작성 ┘
                          ↑ 사람의 구체적 수정 요청 ─┘
```

LLM Agent는 요건·상품 영향·제안의 3개다. `verify`는 출처·값 검사와 재작성 의견 검토를 담당한다.
중간 승인, 코드 패치, 테스트 생성, demo는 없다.

## 실행

`agent/`에서 실행한다. `.env.example`을 참고해 `agent/.env`에 `OPENAI_API_KEY`, `OPENAI_MODEL`을 설정한다.
CLI는 실행 위치와 관계없이 `run.py` 옆 `.env`를 읽으며 같은 이름의 기존 환경변수보다 우선한다. 키를 커밋하지 않는다.

```bash
uv sync
uv run python run.py --article 8  # 실제 LLM + 로컬 자료로 DSR 변경 확인
uv run python run.py              # 실제 LLM + 로컬 자료로 전체 변경 확인
uv run python run.py --mode live             # 실제 MCP 자료
uv run python run.py --mode llm --article 8 --verbose  # 요청 로그
uv run pytest -q
```

기본 모드는 `llm`: 실제 모델 + 로컬 샘플이다. 기본 실행도 API 사용량이 발생한다.
`--article`은 변경 본문의 조항 ID이며 여러 번 지정할 수 있다. 부칙과 관련 규정은 계속 읽는다.
검토는 항상 사람이 한다. 자동 승인 옵션은 제공하지 않는다.

로컬 샘플은 저장소 루트 `data/`의 가상 자료다.
규정 4개, 상품 12개, 규칙 82개, 상품 설명서 12개를 읽는다. 계약 120건의 개별 영향 조회는 아직 연결하지 않았다.
규칙은 개정 시행일 전날의 유효 행만 사용한다. 종료·미시행 행은 현재 값으로 쓰지 않는다.
상품 영향은 4개씩 나눠 모든 상품을 분석한다. 정답지 `eval/`은 모델 입력·런타임 검증에 쓰지 않는다.

## 검토 화면

기본 화면은 `번호 | 상품 | 변경 대상 | 현재→제안 | 적용 범위 | 상태` 요약표다.
승인 항목은 숨기고 원래 번호를 유지한다. 명령은 한 번에 하나씩 입력한다.

| 입력 | 동작 |
|---|---|
| `v 3` | 3번 상세 보기. 모델 호출 없음 |
| `k` | 변경 불필요 판단과 이유 보기 |
| `p 1,3` | 1·3번 승인 |
| `p P001` | P001 상품의 제안 승인 |
| `r 2` | 2번 제외 |
| `c 2` | 의견 입력 후 2번 재작성·검증 |
| `e 2` | 2번의 요약·조치·추가 제안·주의 직접 수정 |
| `a` | 남은 대기 항목 전체 승인 후 완료 |
| `r` | 남은 대기 항목 전체 제외 후 완료 |
| `f` | 모든 항목이 승인·제외되었을 때 완료 |

검토 단위는 상품 × 변경 요건이다. 의미 있는 복수 규칙 변경은 지원하며 임의로 한 규칙만 허용하지 않는다.
각 제안의 `target_rule_ids`는 바꿀 규칙, `evidence_rule_ids`는 참고한 규칙이다.
`현재`에는 변경 대상만 표시한다. 유지·절차 확인에는 숫자 변경을 만들지 않는다.

## 제안과 검증

- 필수 값 변경은 규칙 ID·키·현재 값·제안 값·원래 단위로 구조화한다.
- 단일 수치가 명시된 실제 개정 원문에서 코드가 값을 계산한다. ratio 0.35와 percent 35를 구분한다. 모델이 이 값을 다시 생성하거나 재작성 중 대체하지 않는다.
- 모호한 계산식·수치가 없는 의무에 억지로 값을 만들지 않는다. 신규 규칙 등록은 별도 구현 범위다.
- 요약 220자, 필수 조치 최대 3개, 요청받은 추가 제안 최대 2개, 주의 최대 2개로 제한한다.
- 시행일·경과조치는 비교 자료와 부칙 원문에서 가져온다.
- 조건부 예외는 적용 범위와 원문 인용을 함께 둔다. 차주별 수치형 DSR 예외 한도만으로 상품 전체를 면제하지 않는다.
- 인용문이 실제 조회 원문과 일치하는지 검사한다. URI가 틀렸어도 원문이 유일하게 식별되면 그 조회 URI로 바로잡는다. 모호하면 추측하지 않는다.
- 적용 조건의 인용을 보완해도 근거가 확인되지 않으면 확인 필요로 돌리고 값 변경 확정 대상에서 뺀다.
- 현재 값·키·단위·시행일·변경 대상 일치 여부를 검사한다. 이미 같은 값인 규칙 변경은 거부한다.
- 검증 실패 시 해당 항목만 한 번 더 작성한다. 자동 보완은 같은 버전 안에서 수행한다. 실패가 남으면 승인할 수 없다.

이 검사는 모든 법령 의미 판단의 정답을 보장하지 않는다. 적용 예외·규칙의 업무상 의미는 사람이 근거와 함께 검토한다.
`needs_review` 승인은 확인 필요 제안서의 검토 결과이며 실제 DB 반영 승인이 아니다.

## 수정 요청

`c 2`에서 "다른 제안 줘봐"처럼 대상을 특정하지 않는 대표적인 모호한 요청은 구체화를 안내한다.
"새로운 제안"만 입력해도 구체화를 안내한다.
예: "필수 DSR 변경은 유지하고, 고객에게 보여줄 신청 화면 안내 한 문장을 추가 제안으로 써줘."

재작성은 선택한 항목에만 이전 검토본·의견·필수 값·적용 조건을 전달한다.
필수 값·시행일·적용 범위는 유지하고 부가 아이디어는 `optional_actions`로 분리한다.
변경된 본문이 있는지와 요청의 의미가 실제 반영됐는지를 검사한다. 의미 검토는 별도 LLM 호출이며 실패하면 한 번 보완한다.
끝내 실패하면 기존 본문을 보존하고 승인 차단 사유를 표시한다. 다른 항목의 승인·내용·버전은 유지한다.
상세 화면에서 요청 의견·반영 설명·변경 항목을 확인할 수 있다.

직접 수정은 값·단위·근거·시행일을 바꿀 수 없다. 본문을 검증한 뒤 버전을 올려 대기로 되돌린다.
이미 승인한 항목도 완료 전 다시 수정할 수 있다. 오래된 버전·중복 ID·잘못된 일괄 결정은 반영하지 않는다.

## 연결 범위와 파일

| 파일 | 역할 |
|---|---|
| `run.py`, `app/cli.py` | 실행 설정·요약·상세·검토 입력 |
| `app/graph.py`, `app/state.py` | 노드 순서·분기·공통 상태 |
| `app/nodes/requirement.py`, `impact.py` | 변경 요건·전체 상품 영향 |
| `app/nodes/proposal.py`, `verify.py` | 제안·검증·선택적 재시도 |
| `app/nodes/review.py`, `report.py` | 항목별 검토·결과 |
| `app/validation.py` | 값·조건·출처·입력 검사 |
| `app/llm.py`, `prompts/` | 구조화된 모델 호출과 단계별 지시 |
| `app/tools/local.py`, `app/data.py` | 로컬 규정·유효 규칙·상품 문서 조회 |
| `app/tools/mcp_client.py` | 규정·업무 MCP 조회 |
| `app/runner.py`, `backend.py`, `schemas.py`, `reasoning.py` | 시작·재개·연결 계약·모델 인터페이스 |

현재 조회 순서는 코드가 정한다. 모델이 MCP 도구를 자유롭게 선택하는 루프는 아직 없다.
`live`는 `REGULATION_MCP_URL`, `BUSINESS_MCP_URL`을 쓴다. code-mcp는 사용하지 않는다.
live는 최신 MCP의 `list_regulations` → `list_articles` · `get_article`, `get_product_doc`, `get_products`, `get_product_rules(as_of=기준일)`을 호출한다.
관련 규정은 개정 시행일에 유효한 버전을 고르고, 상품 문서는 서버가 준 `doc://상품#섹션` URI를 인용 근거로 유지한다.
시작할 때 서버 도구 목록을 검사한다. 구버전 MCP면 최신 main에서 서버를 다시 실행하라는 오류를 낸다.
문서가 없으면 자료 누락으로 표시하며 로컬 자료로 대체하지 않는다. 백엔드 DB는 Git의 data 파일을 받는 것만으로 갱신되지 않는다.

Docker를 사용한다면 최신 main을 받은 뒤 규정·업무 MCP 이미지를 다시 빌드한다. 서버 실행 설정은 [MCP 안내](../mcp/README.md)를 참고한다.

`AgentRunner.start_backend` / `resume_backend`와 camelCase payload 변환은 연결 지점이다.
현재 HTTP 서버·콜백·쓰기 도구·대기열·실제 상품 반영은 구현하지 않았다.
`backend.py`의 변환은 연결 초안이며 최신 백엔드의 제안 저장·승인 API 계약과 맞추는 작업은 별도다. MCP를 통한 백엔드 조회와 이 HTTP 연결을 구분한다.
검토 체크포인터·이력은 프로세스 메모리에 있으므로 종료 시 사라진다. 서비스 연결 때 인증·영구 저장·분산 잠금이 필요하다.

커밋은 매번 사용자의 명시적인 허락을 받은 뒤 수행한다.
